【这是什么】
  一个可直接 push 到 GitHub 的最小 Xcode 工程。它【不依赖】原来的 TSL-IOS.ipa，
  也不包含任何微信/小程序代码，而是按已还原的 BLE 协议直连 TSL 加装模块
  （FFF0/FFF1，默认密码 1234，1.5s 一回 176 帧），自己解析车速后送到：

    ① Live Activity（锁屏 / 灵动岛 / iOS 26 原厂 CarPlay Dashboard）
       —— 秒级实时的主载体，数据走 ActivityKit ContentState，不需要 App Group
    ② WidgetKit systemSmall（iPhone 桌面 / 锁屏 / StandBy / CarPlay Dashboard）
       —— 同一个小组件代码自动上桌面和车机；需要 App Group 才能读到数值
    ③ 主 App 全屏仪表（前台常亮，也可作 AirPlay 镜像兜底）

  GitHub Actions 的 macos-26 runner（默认 Xcode 26.6）会在云端编译并产出
  【未签名 IPA】。GitHub runner 无法登录你的 Apple ID，所以最后一步签名必须
  在你自己的 Windows 电脑上完成。

【1. 一次性准备】
--------------------------------------------------------------------------------
  1) GitHub 账号（免费即可），新建一个 Public 仓库，例如 TSLGauge。
  2) 把本目录【所有内容】上传（含隐藏的 .github 目录）：
       网页上传：把除 .git 外的文件打包 zip，在仓库页 Add file → Upload files
       命令行：  git init && git add . && git commit -m init
                && git remote add origin <你的仓库地址> && git push -u origin main
     ⚠️ 必须让 .github/workflows/build-unsigned-ipa.yml 位于仓库根目录的这个路径，
        否则 Actions 不会触发。
  3) Windows 准备自签工具（二选一，见第 4 节取舍）：
       Sideloadly（sideloadly.io）或 AltServer + AltStore（altstore.io）
       以及免费的 Apple ID（建议专门注册一个，不要用主账号）。
  4) iPhone 开启开发者模式（iOS 16+）：设置 → 隐私与安全性 → 开发者模式。

【2. 触发构建】
--------------------------------------------------------------------------------
  仓库页 → Actions → 左侧 "Build unsigned IPA" → Run workflow，填三个输入：

    app_group_id   可留空。若你的签名工具能创建 App Group，填形如
                   group.com.yourname.tsl.speed（见第 4 节）。
                   留空时构建会写入内部哨兵 __NO_APP_GROUP__（Info.plist 里
                   看到它属正常，代码会当作「不启用」处理）
    bundle_id      默认 com.tsl.gauge。若要改，用反向域名，且别和已装 App 冲突；
                   Extension 会自动变成 <bundle_id>.widgets
    display_name   默认「TSL 车速」

  构建约 5~15 分钟（首次 brew install xcodegen 会慢些）。
  成功后在该次 run 页面底部 Artifacts 下载 TSLGauge-unsigned-ipa，
  解压得到：
       TSLGauge-unsigned.ipa    ← 拿去自签
       build-info.txt           ← Xcode 版本 / App Group / SHA256 / IPA 结构
  失败时会自动上传 xcodebuild-log，先看日志末尾的错误再改。

  构建脚本会自动校验：
       · Payload/TSLGauge.app/PlugIns/TSLWidgets.appex 是否存在（缺了小组件就没了）
       · UIBackgroundModes 是否含 bluetooth-central
       · NSSupportsLiveActivities / NSExtensionPointIdentifier
       · 两个 Info.plist 的 TSLAppGroup 是否已展开且一致
       · 是否确实未签名（无 _CodeSignature / embedded.mobileprovision）
  任何一项不过都会让 workflow 变红，避免拿到一个装不上或没扩展的坏包。

【4. 自签安装 —— 决定桌面 Widget 能否显示数值的关键一步】
--------------------------------------------------------------------------------
  ⚠️ 无论用哪个工具，遇到「是否保留 App Extensions / Keep Extensions」
     必须选【保留】。选错的话 .appex 会被剥掉，桌面小组件和实时活动全消失。

  两种工具的取舍（这是本方案唯一还需要实机验证的不确定项）：
   A) AltStore / SideStore（推荐先试）
      会为每个 App 和 Extension 注册显式 App ID，社区实践支持创建
      application-groups（通常有 2~3 个上限）。若成功，桌面 Widget 能读到速度。
      安装后可用 iOS 上的 ESign/Apps Manager 或 macOS 的
        codesign -d --entitlements :- Payload/TSLGauge.app
      检查主 App 与 .appex 是否都有同一个 com.apple.security.application-groups。
      → 若确认拿到了 App Group：重新跑一次 workflow，把【完全相同的】
        group ID 填进 app_group_id，再签一次，桌面 Widget 才会显示数值。
      顺序不能反：先签名拿到 group ID，再回填重新构建。
   B) Sideloadly
      免费 Apple ID 下常用通配 App ID（TEAMID.*），通配 profile 通常带不了
      App Group。此时桌面 Widget 会显示「打开 App 查看实时车速」（不冒充数据），
      但【Live Activity 完全可用】—— 锁屏、灵动岛、iOS 26 原厂 CarPlay
      Dashboard 上的秒级实时车速照常工作，因为它的数据不经过 App Group。
      在 Sideloadly 的 Advanced 选项里若有 App Group / 显式 App ID 相关设置，
      可尝试按 A 的方式打通。

  安装步骤（以 Sideloadly 为例）：
    1) iPhone 用 USB 连 Windows，信任此电脑。
    2) Sideloadly 拖入 TSLGauge-unsigned.ipa，填 Apple ID，点 Start。
    3) 出现 App Extensions 选项时选【保留】。
    4) iPhone：设置 → 通用 → VPN 与设备管理 → 信任开发者。
    5) 打开 App 一次：授权蓝牙、启动 Live Activity、保持屏幕常亮。
       模块默认密码 1234，若改过，在 App 首页输入框里改「应用密码」。
    6) 有效期 7 天；AltStore/SideStore 可在同 WiFi 下后台自动续签，
       Sideloadly 需每 7 天手动刷新一次。

【6. 秒级实时在哪里成立、在哪里不成立（务必如实理解）】
--------------------------------------------------------------------------------
  ✅ Live Activity：BLE 后台 bluetooth-central 唤醒进程 → 本地 Activity.update
     （pushType: nil，不需要 APNs / 付费账号）→ 约 1~2 秒级。
     这是锁屏、灵动岛、CarPlay 上真正可靠的实时通道。
     断流 8 秒后 staleDate 到期，界面自动变「数据已过期」，不会拿旧车速冒充实时。
  ✅ 主 App 全屏仪表：前台常亮（isIdleTimerDisabled = true）时逐帧刷新。
  ⚠️ 桌面 Widget：主 App 前台时 reloadTimelines 不计入 WidgetKit 预算，
     可做到约 1~2 秒级；iPhone 锁屏后主 App 不再前台，退回带时间戳的快照，
     界面会明确标「实时 / 快照」。CarPlay 连接时手机通常锁屏 →
     【车机上的可靠秒级实时靠 Live Activity，不是靠 Widget】。
  ❌ 不存在的能力：Widget Extension 自己连 BLE、Widget 严格 1.5s 刷新、
     APNs 推送更新 Live Activity、后台被彻底杀死后自动复活。
     上车前手动打开一次 App 是必需动作。

  ⚠️【重要：BLE 单连接互斥】绝大多数 BLE 外设同一时刻只允许一个 Central 连接。
     TSL 模块被原来的「TSL模块管理」App 连着时，本 App 会扫到但连不上
     （或反复断开）。行车时请【不要同时运行原 App】：
       · 要么完全用本 App 接管 BLE（推荐）；
       · 要么在原 App 里主动断开蓝牙后再切到本 App。
     同理，两台 iPhone 不能同时连同一个模块。若出现「正在连接 → 已断开」
     循环，第一件事就是检查原 App 是否还占着连接。

【9. 界面定制：纯速度 7 段数码管（2026-11-18 变更）】
--------------------------------------------------------------------------------
  需求：一个界面极度纯粹，只显示速度；字号尽量大；7 段码字形；
        0~60 绿 / 61~100 黄 / >100 红。

  实现决策：不用第三方字体，改用 SwiftUI 原生绘制标准 7 段数码管
    · iOS 系统没有内置 7 段码字体；引入 TTF 需要 UIAppFonts 注册、
      字体许可、CI 资源打包，Widget Extension 在自签下最容易出问题。
    · 自绘方案零字体文件、零许可风险、任意尺寸自适应、颜色精确可控，
      还能画出「熄灭段」（同色 13% 透明度），质感比字体更接近真实数码管。
    · 每段画成带斜切端点的六边形；每位数只需 2 个 Shape（暗底 + 点亮），
      Widget 渲染开销极低。

  落点（三个界面共用同一个 SevenSegmentSpeedView，视觉完全一致）
    ① 桌面 / iOS 26 原厂 CarPlay Dashboard 的 systemSmall Widget
       —— 【最纯粹】：整个画面只有数字，无标题 / 单位 / 档位 / 时间戳 /
          实时快照文字。背景近黑（white 0.03），数字按可用空间撑到最大。
    ② 锁屏 / 灵动岛 / 车机 Dashboard 的 Live Activity
       —— 同样只有数字，额外一个 5pt 状态点（绿=实时、橙=过期）。
    ③ 主 App 全屏仪表 —— 同样的大号数码管（AirPlay 镜像兜底画面）。

  分段配色（SpeedPalette.color，按原始数值，不区分 KM/H / MPH）
       0 ... 60    绿色  rgb(0.16, 0.88, 0.36)
      61 ... 100   黄色  rgb(1.00, 0.78, 0.10)
      > 100        红色  rgb(1.00, 0.24, 0.22)
      无有效读数（档位无效 / 断连 / "--"）  灰色
    注：这是车速警示配色，与金融场景「红涨绿跌」无关。
    Live Activity 的 ContentState 新增 speed: Int? 字段，
    Extension 直接用数值取色，不需要解析 "--" 之类的显示串。

  不冒充实时的处理
    · 数据为快照 / 超过 300 秒 / BLE 断连 → 数字整体降到 55% 不透明度
    · 完整状态写在 accessibility label / value（VoiceOver 与车机朗读可读）
    · 想要肉眼可辨的状态标记：把 SevenSegmentSpeedView 的 showsStatusDot
      设为 true（SpeedWidget.swift 里那一行 false 改 true 即可）
    · 签名工具没给 App Group 时，共享容器读不到，Widget 会显示灰色 "--"
      （不冒充数据）；此时桌面无数值，但锁屏 / 灵动岛 / 原厂 CarPlay
      Dashboard 的 Live Activity 仍有秒级实时车速，见第 4、6 节。

  可选：如果你坚持要「真正的字体文件」
    1) 下载开源 DSEG7（keshikan，免费许可）的 .ttf 放进仓库
    2) 两个 target 的 Info.plist 加 UIAppFonts 数组列出文件名
    3) project.yml 的 sources 追加字体目录，确保被 Copy Bundle Resources
    4) 把 SevenSegmentNumber 换成 Text(...).font(.custom("DSEG7 Modern", size:))
    代价：许可、资源打包、Widget 字体注册时机都需要实机验证；
    自签 + CI 场景不推荐，当前自绘方案更稳。

  自检：python scripts/verify_seven_segment.py
    从 Swift 源码解析 a~g 位定义与 case 表，逐项比对标准 7 段真值表
    （0~9 与 '-' 共 11 个字形），并验证 0/60/61/100/101 等配色边界，
    另检查界面纯净度与 systemSmall（CarPlay 必需）是否被误删。已全部 PASS。

【11. 连接诊断：修复「FFF1 特征不完整」+ 全链路日志（2026-11-18 变更）】
--------------------------------------------------------------------------------
  你反馈：无法判断有没有连上蓝牙，界面只显示「FFF1 特征不完整」。
  根因（对照原小程序 app-service.js 的 BLE transport 逐字还原）
    原实现做了两个错误假设：
      ① peripheral.discoverCharacteristics([FFF1], for: service)
         —— 只发现 FFF1 一个特征，【漏掉了负责通知的 FFE0】
      ② 假设 FFF1 同时具备 write + notify，否则直接报「特征不完整」
    原 JS 的真实规则是：
      服务    = UUID 字符串含 FFF0
      写特征  = UUID 含 FFF1 且可写（找不到才报「未找到写特征（FFF1）」）
      通知特征= FFF1 同时「可通知 + 可写」→ 用 FFF1
                否则 → 找 UUID 含 FFE0 的特征（原 JS 甚至不检查它的 notify 属性）
                都没有 → 抛「未找到通知特征（FFF1/FFE0）」
    很多 TSL 模块正是「FFF1 只写、FFE0 负责通知」的形态，所以必然卡死。

  已修复（Sources/App/TSLBLEManager.swift）
    ~ 服务与特征全部改为【全量发现】（discoverServices(nil) /
      discoverCharacteristics(nil)），并把实际服务 UUID、每个特征的
      UUID + 属性（read/write/writeNR/notify/indicate）全部写进日志和诊断页。
    ~ 按上面的 JS 规则选写特征与通知特征；通知候选按优先级排队，
      订阅失败 / isNotifying=false / 超时会自动换下一个（FFF1 → FFE0 → 其它）。

【11B. 真机日志修正：160 帧认证看错字节（2026-11-23 变更）】
--------------------------------------------------------------------------------
  你发来的真机日志：这次连上的是真模块 TSL6（名称含 TSL、RSSI -73），
  特征选择全对（FFF1 write+notify）、订阅成功、收到 7 帧，
  但一直停在「等待认证」，反复「重新提交密码」。

  根因（逐字节对照原小程序 app-service.js）
    原 JS 解析 160 设备信息帧：
        s = e[3] || 0                    ← payload[3] 才是 runtimeFlag
        runtimeReady = 1 == (1 & s)      ← 只看最低位
        handleDeviceRuntimeProof:
          160 帧累计 >= 2 且 runtimeReady → completeBleAuth("160x2")
    我们的旧代码却用 payload[0]（那是 hw_ver，实测 0x00）!= 0 判定，
    于是模块明明已经发了 5 次 160 帧证明运行固件就绪，我们死活不认。

    关键事实：原 App 的认证有两条并行路径——
      ① 168 密码校验正确 → 再等 160 确认
      ② 直接 160x2 + runtimeReady → 认证成功（authProof="160x2"），
         不需要 168 密码验证通过
    所以「168 返回密码不匹配」在真机上并不致命，不该把链路判死。

  已修复（Sources/App/TSLBLEManager.swift）
    ~ 160 帧改看 payload[3] & 1 判 runtimeReady；payload[0] 只记日志当 hwVer。
    ~ 160 帧累计 >= 2 且 runtimeReady → completeAuth(proof: "160x2 运行固件就绪")，
      不再依赖 168 密码回包。
    ~ runtimeFlag 最低位 = 0 → 明确提示「模块处于 BOOT/DFU 升级引导模式，
      运行固件未就绪」并给可行动建议（退出升级模式 / 重新上电）。
    ~ 168 code=0 不再把状态卡成「蓝牙密码错误」，改为「密码校验未通过，
      等待 160x2 证明」，继续等 160 帧完成认证。
    ~ 160 帧日志现在打印 hwVer / runtimeFlag / runtimeReady / proofCount，
      下次导出诊断可直接看到模块上报的就绪标志到底是 0 还是 1。

  验证：python scripts/verify_ble_diagnostics.py 新增 1B 节 7 项检查
    （runtimeFlag 取 payload[3]、最低位判定、160x2 不依赖密码、去掉
     payload[0]!=0、168 不判死、认证日志带依据），全部 PASS。

  ⚠️ 若新版本仍停在「等待认证」：导出日志看 160 帧那一行的
     runtimeFlag=0x?? 与 runtimeReady=true/false：
       · runtimeReady=true 但帧数不涨 → 看门狗是否重发 160（每 10s）
       · runtimeReady=false → 模块确实在升级引导模式，先退出 DFU / 重新上电
